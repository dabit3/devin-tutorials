# Prompt: create an in-depth Devin feature tutorial (step by step)

For a short, diagram-led concept video ("how it works and what you can do") use [OVERVIEW_PROMPT.md](OVERVIEW_PROMPT.md) instead.

Copy everything below the line into a new Devin session. Fill in the three fields at the top; leave the rest unchanged.

---

Create a polished tutorial video that teaches new users how to use one Devin feature, and open a PR that adds it to `dabit3/devin-tutorials` under `tutorials/<NN>-<slug>/`.

- **Feature:** <name of the Devin feature, e.g. "Playbooks">
- **What the viewer should be able to do afterwards:** <one sentence>
- **Docs / reference material:** <link or pasted docs, repo to use (mention it with @owner/repo), environment (Linux/macOS/Windows)>

## Scope and accuracy

- These are reusable production rules from tutorials 01–34. A per-video brief can add constraints to that deliverable, but they do not become shared defaults. Tutorial 35 / conference-reel directions stay confined to that reel: do not import its silent format, palette, layout, fresh-footage mandate, testing-hero story, chapter count, animation geometry, pace or lengths. Keep independently approved pre-conference rules, including light mode, readable captions and restrained animated highlights.
- Check current official docs and the product before scripting. Use only supported features and primitives; omit deprecated features entirely, including migration asides. Do not invent settings, picker choices, limits or guarantees. Older capture notes below are examples to reverify, not current UI guarantees. Use current Customize routes for plugins/MCPs and Customize → Memory, not obsolete settings paths.
- Open by explaining what the feature does and why it matters in plain language. Before a demo prompt, explain the task and expected outcome. Teach the real golden path and visible payoff, not just clicks.
- Use the right proof: simulation is not a hardware test, a conceptual Slack diagram is not live Slack evidence, and an Android emulator in an Ubuntu blueprint is not an Android platform-picker option. Cite real sources and record actual actions. Disclose any deliberately planted demo bug in both captions and narration; never present it as an accidental mistake. Show failure/fix/retest only when it genuinely happened, and say exactly which checks ran.

## How to build it

Use the existing kit in `tutorials/_kit/` (capture over CDP, deterministic 4K Canvas renderer, synthesized audio, `build.sh`), and follow `tutorials/README.md`. Copy the structure of the most similar existing tutorial folder (`capture.mjs`, `shots/beats.json`, `spec.js`). Prefer a macOS capture VM for new tutorials; the demonstrated session's platform must still match the feature/brief.

1. **Plan first.** Read the docs, then write a short shot list of 6–12 beats: the golden path from a clean start to a visible end result. Each beat is one action plus one short caption. Narration uses fewer complete sentences across related actions, not a fragment for every click.
2. **Use the demo account.** Record in the `thequantexplorer` Devin org (account eigenexplorer@gmail.com), normally with demo repos under `thequantexplorer/*`. Check existing authentication before asking for sign-in. If `DEVIN_WEB_LOGIN_EIGENEXPLORER` is available, import it into capture Chrome with `CDP=http://127.0.0.1:9333 DEVIN_WEB_LOGIN="$DEVIN_WEB_LOGIN_EIGENEXPLORER" node _kit/tools/devin-login-import.mjs` from `tutorials/` (expect `https://app.devin.ai/org/thequantexplorer`; never print or commit the secret). If missing/expired, ask for sign-in through the Desktop tab. Use an explicitly approved alternative account/repo when an integration needs it, such as Slack's linked org; confirm access before filming. Ask before creating or pushing a demo repo somewhere new.
3. **Clean the account.** Inspect earlier takes, open PRs, profiles, automations and demo-account memory for stale work or answers that contaminate the story. Archive only authorized demo sessions from this task; keep PRs open unless closing them was approved. Never mass-archive unrelated sessions, revert demo main, merge PRs, delete resources or edit memory without authorization. Save a copy before approved memory cleanup, then ask Devin to forget/update only demo-specific entries. Use `HIDE_TEXT="<title>"` only for unrelated sidebar clutter, never to alter demonstrated state/chronology. Repeat authorized cleanup between takes and report changes.
4. **Capture the real app.** Drive a signed-in Devin web app in Chrome through CDP (`127.0.0.1:9333`) and take a screenshot per beat. Mask the account email name (`MASK_TEXT=<email name>`). Before capturing, make sure there are no setup warnings, dismissible banners or notifications under the prompt box or floating announcement cards on the home page (dismiss them with their real close button, never paint them out), stale failed sessions in view, or real secrets on screen (use obviously fake demo values and delete them afterwards). Wait until the sidebar session list has loaded (no skeleton rows) before the first screenshot. If a live take is not smooth, re-capture it. A faithful reconstruction from genuine footage can repair presentation only; never invent a control, action, output or test result.
5. **Edit in `spec.js`.** Holds, captions, speed badges, skips. A `poll` beat lasts as long as the real gap to the next kept poll (divided by `speed`), so when you skip a range, give the last kept poll before it an explicit `hold`. Otherwise the whole skipped wait comes back as one long still. Don't keep frames showing questions or answers the video never explains; skip them or answer them on camera. When only the edit changes, change `spec.js` and rebuild; don't re-record. Put caption fixes in both `spec.js` (as an override) and `capture.mjs` (for future takes).
6. **Build.** From `tutorials/`, run `bash _kit/tools/build.sh <folder>` with the bare folder name (a `tutorials/<folder>` path fails with a `render.mjs` usage error) and wait until the log prints `built <folder>/…mp4` before touching the MP4 (it isn't playable until then). Then make a 1080p preview for review. 4K renders can need several GB free for frames (or set `SEG=1500` to render and encode in segments); if disk is tight, build with `JPEG_QUALITY=80`, delete old `build/` frame dirs, clear `npm cache` and Chrome's cache over CDP (`Network.clearBrowserCache`). Never run two `build.sh` for the same folder at once: they share `<folder>/build/`, one fails, and the old MP4 stays, so check the MP4's mtime. The iOS Simulator devices in `~/Library/Developer/CoreSimulator` are the biggest reclaimable space on the Mac; ask before deleting them. Before a full build, check caption placement and zoom cheaply with `node _kit/tools/render.mjs <folder> --every 30 --out <dir>` and look at the stills. On Linux, `render.mjs` with several workers stalls on `Page.captureScreenshot` timeouts: run two `render.mjs <folder> --workers 1 --from A --to B` processes over split frame ranges (about 9 fps each), then `SKIP_RENDER=1 bash _kit/tools/build.sh <folder>` after checking that installed ffmpeg supports the flags in the current build script. A 4K encode of about 11k frames takes about 25 min.
7. **Review the frames.** Pull frames every few seconds, at every caption and at any timestamp the reviewer mentioned, and look at them. Check that each click lands on the control the caption describes, that each caption matches what is on screen (e.g. don't say "opened devin.ai" when Devin's browser shows the app on `localhost`), that no text is oversized or half-loaded, that the cursor isn't parked somewhere misleading, and that the sidebar has no stale sessions. Fix and rebuild before handing off.

## Every narrated action must be real
- If a caption says "click X", the capture must click the actual X control, and the script must confirm the click did what the caption says. Otherwise fail the capture instead of recording the shot.
- Find targets by their real DOM element and position, never by a loose text match that could pick a nearby look-alike. For example, a citation demo must click a `file:line` citation link (`span[role=link]`) inside Devin's answer in the chat, not a file link in the code panel. Pick a citation whose lines aren't already on screen, so the jump is visible, then check that the code panel scrolled to those lines.
- Don't show a step whose result is already on screen. For example, if the PR view is already open, switch the panel back first, then open the PR from the PR card in the chat, and check that the PR view opened.
- Wait for the real UI before acting: poll with `p.evaluate(...)` plus a short `sleep` (the CDP page object has no `waitForFunction`), e.g. wait up to 30 s for the session link to appear in the sidebar before clicking it. Start each session exactly once; if a retry starts a duplicate, stop and archive it.
- The command palette is always in the DOM as a hidden `[role=dialog]`, so check that a dialog is visible before treating it as a confirmation. Wait for `main [contenteditable]` before clearing or typing in the home composer; it isn't mounted right after `goto`.
- Every poll beat without a `hold` lasts real gap ÷ `speed`, so a long wait you keep in shots/ can add minutes. Skip the polls you don't need in spec.js, and check `node _kit/tools/render.mjs <folder> --count` from `tutorials/` before building.
- "Devin is just working" stretches should normally play in about 2–2.5 s, with no more than roughly 3 s of inactivity. Start with `pollRunMax: 2.2` in `spec.js`; it compresses eligible plain polls (no explicit `hold`, ring or new narration), not every beat. Inspect explicit holds/rings separately and label compressed work honestly with a "Sped up" badge.
- If render.mjs fails with "Timed out after 30000 ms while waiting for the WS endpoint URL", headless Chrome is just starting slowly (about 15 s on a busy Mac, with leftover `puppeteer_dev_chrome_profile-*` dirs in `$TMPDIR`). The launch now waits up to 180 s. Delete stale profile dirs between builds.
- Capture helpers (`r.poll`, `r.clean()` in `_kit/capture/rec.mjs`) skip frames with loading skeletons, oversized text (over 24 px), a terminal (xterm) canvas drawn at the wrong pixel ratio, which shows up as giant terminal text in the Progress panel, or the empty new-tab picker. Keep that on, and never ship a frame that shows those states.

## Style rules
- Pages that scroll the window (GitHub, docs) must capture the viewport at `scrollX/scrollY`, not document (0,0). Current `_kit/capture/cdp.mjs` already handles this; check main before copying an old override. Older frames shot at document (0,0) have a blank top band: re-capture them, or save them with a `camForce` zoom that crops below the band.
- To bring text inside a nested scroll container on screen (e.g. the Devin Review discussion), set `scrollTop` on its nearest scrollable ancestor; scrolling the window does nothing there.

**Format**
- 3840×2160, 60 fps, 16:9, H.264 High, AAC 48 kHz.
- Open on the Devin logo and a short title with a one-line subtitle. Never write "Devin tutorial" on the title card.
- End on the outro card with a short takeaway line.

**Pacing**
- Length is whatever the flow needs. Most run 45–90 s, and long agentic flows can run longer.
- Every caption stays on screen long enough to read: at least about 2.6 s, longer for long captions. The video itself slows down to make room; the caption is not just left up longer over faster footage.
- No dead air. Cut or speed up waits, and show long Devin work as a short sped-up montage (about 10–12 s, with a "Sped up" badge). Code being written gets 7 s at most. Focus on the result, not every step.
- Jump straight to results. About 2–3 s after the last "watch it work" caption, cut to the finished PR with a caption like "When Devin is done, it opens a PR and offers to test it", skipping the polling in between. After a click that starts something (e.g. `Test…`), the next visible change (e.g. the Computer tab) should come within about 3 s.
- Never make the viewer wait on typing. Short prompts can type in with typing sounds that match the visible text. For long or pasted prompts, drop the finished prompt in at once as a still beat (`kind: 'still'`), with no typing sound. Typing at `cps: 16` read as too slow in the narrated Memory video; use about `cps: 48` (3x) for typed prompts. Hard limit: if a prompt would take more than 3 s to type at 48 cps (about 140 characters), don't type it at all: `skip` the typing beats and show the finished prompt as a `kind: 'still'` beat.

**Camera**
- **Nader's standing layout rules (every tutorial from 19 on):** (1) collapse the left sidebar whenever the step isn't using it; (2) inside a session, collapse the right tabs panel whenever it's empty or unused; (3) put an elegant animated border on anything the narration or caption points at that isn't obvious; (4) capture at 125% browser zoom ("zoom in by 1 degree"). Check every frame sheet against these four before calling a cut done.
- Zoom: 125% is one Chrome step above the old 110% baseline (tutorials 01-13 and 15-18 used 110%). The kit default in `_kit/capture/cdp.mjs` is still 1.1, so set `ZOOM=1.25` on every capture command. Apply it before the first screenshot, keep it for the whole take, and check a frame to make sure nothing important is cut off at 1440x810. At 125% the page lays out at 1152x648 CSS px, so right-edge controls can fall off-screen (the Save button of a new row in Settings → Devin Review only shows once the settings sidebar is collapsed).
- Panels: collapse the left nav with `aria-label="Collapse sidebar"` (Ctrl+B toggles it). Open it only for an action that needs it (e.g. clicking Settings), then collapse it again. In a session, hide the right tabs panel with `aria-label="Hide tabs panel"` when it's empty (it shows "Watch and control Devin's Computer"). Open it only when it shows something (Findings, a PR, the Computer tab). Run a `tidy()` after every navigation and during polling that collapses both and dismisses banners; copy it from `14-devin-code-scans/capture.mjs` or `19-managed-devins/capture.mjs`.
- Annotations: two engine options draw the same thin, 2 px blue rounded border that animates in with a soft glow. Use at most one per step, and keep them identical in the voiced and unvoiced cuts. Boxes are center + size in 1440x810 frame coordinates. Captions anchor to the annotated box.
  - `ring: {x, y, w, h}` or `ring: true` (the beat's `target`): draws in with a slight scale and no dimming, and stays on that shot until it's replaced (it fades 0.35 s before the next image). `ringFor: <s>` ends it early, `ring: false` clears it, and `ringPad`, `ringRadius` and `ringDelay` tune it. This is the default (tutorial 19).
  - `hl: true` (the beat's recorded `hlBox`, else its `target`), `hl: {x, y, w, h, pad?}`, or an array of boxes to outline several things at once (tutorial 20; `rec.rect(target)` in capture returns a box, and `hl` arrays in recorded beats are scaled to frame px): also dims the rest of the frame by 10% (`hlDim` in spec.js; set `hlDim: 0` for no dim) and fades out at the next beat unless that beat has `hl: 'keep'`. If the beat scrolls or changes screen, add `hlDelay: 0.75` so it lands after the transition (tutorial 14).
  - Record the real rectangle in capture (`hlBox` from `getBoundingClientRect`, scaled to frame px). Elements you can't find in the DOM, like the inline diff's green added lines, can be measured from screenshot pixels instead. Never point at an area the voice isn't talking about.
- Zoom sparingly, and only early on (home screen, composer, a small setting) when a control would otherwise be unreadable. The kit caps zoom at 1.3×.
- Once you are inside a Devin session (chat, Progress, PR tab, Computer tab, testing), stay zoomed out so the viewer sees the whole UI. Set `noZoom: [['<first session shot>']]` in `spec.js`. `noZoom` drops every `cam` from that shot onward, so a deliberate zoom on a small control after that point needs `camForce: true` on its `cam` entry. Check the rendered frames to confirm the zoom actually shows.
- Never let the cursor cover text the viewer needs to read. Hide it with `cursor: false` while a prompt is on screen.
- The capture cursor is separate from Devin's own pointer inside the Computer tab. While Devin's computer is working (testing, browsing), hide the capture cursor (`cursor: false` on the first beat, `cursor: true` when the next real click comes) so it doesn't sit still on the Computer tab and look like it isn't following the action.
- Cut shots with glitches such as loading skeletons, oversized text or half-rendered panels, and use a loaded frame instead.

**Captions**
- One short, plain-English line per beat (under about 10 words) that says what to do or why it matters.
- Use the kit defaults: 1.18× size, no arrows. Never cover the control being used or anything the viewer needs to read.
- Outside a running session (setup, menus, pickers, dialogs, settings, terminal prompts), put the caption next to the action, in empty space, so the eye doesn't travel to the bottom: set `capPos: 'auto'` and a `target: {x, y, w, h}` (1440×810 CSS px, covering the control or output being described) on that beat. If a list or menu fills most of the screen, use `capPos: 'top'` (or `'bottom'`) instead.
- Inside a running session, use a safe bottom band only if it avoids controls, the composer and described content; otherwise place captions beside the relevant content. Check both cuts, including crossfades.
- Shorten a caption if that's what it takes to fit beside the control (e.g. "Turn on ACP agents like Codex in Settings"). Check rendered stills of every moved caption for overlaps, including the crossfade into the next shot.
- Captions about a whole page/section should stay in a consistent safe position across tour stops (usually `capPos: 'bottom'` where clear). Do not force bottom placement over a composer or described control. Give each stop about 3 s to read.
- Light subtitles only where they help. Don't caption every click.
- Every caption must describe something the viewer can see or understand. Avoid slogans that need explaining (e.g. "Changelog in, docs PR out"); say what is on screen instead.

**Content**
- Show the real product flow: Agent/Ask choice, model and OS pickers where relevant, repos mentioned with `@owner/repo`, and Devin opening the real PR. State the desired deliverable naturally, but do not script hand-held fake success.
- Show Devin's own computer (the Computer tab) when it helps explain the feature, e.g. its browser on a real page.
- In a First Session / Introducing Devin-style demo, use real UI feature work, not a read-only audit. Before an authorized merge, show Devin testing that feature in the browser and the returned recording. Wait for testing to finish; a successful payoff needs a clean passing recording, not an interrupted/failed one. If testing fails, show the honest fix and passing retest when that is the story, or re-record after resolving it. Never claim untested checks passed, hide a merged icon to imply earlier testing, or merge without permission. `_kit/capture/testmerge.mjs` helps with an authorized test/merge flow; check its behavior first.
- When a feature has several modes (trigger types, MCP integrations, natural-language vs form setup), give a short overview of them up front, then walk through one example in detail.
- When Devin can generate a config itself (e.g. Generate with Devin for a scan profile or an automation), show that on camera instead of filling the form by hand, then walk through what it generated, one sentence per section.
- If the feature has a quick "try it now" control (Run automation, Test the app, Merge…), end by pointing it out.
- Keep the account anonymous: mask the email and avoid private repo names you don't need.
- Other sessions in the same account (a parent bot, a teammate) can appear in the sidebar mid-take. Check frame sheets of the sidebar for every phase, add their titles to `HIDE_TEXT` as soon as they show up, and for frames already captured either skip them or frame them out with a `cam` zoom that leaves the sidebar out of view (z 1.3 centred at x ≈ 890 in the 1440 space covers the session pane exactly). Don't paint them out.

**Transitions and emphasis**
- Hold important menus, selected platforms and dialogs for roughly 2.5–3 s, or cut them if irrelevant; never flash meaningful UI for a few frames.
- Inspect transitions at least at 30 fps and at the final exported frame rate, not only one-frame-per-second sheets. A beat's `cam` or `cam: 'reset'` starts at the crossfade start; a tiny `camDur` can jump the outgoing shot. Prefer flat cuts or gentle, properly timed moves that leave the outgoing shot stable.
- Remeasure `hlBox` after slide-in dialogs settle; the early box may be offset. Inspect rings at line starts and through fades. Never ring a target before it is visible.

**Audio**
- The music bed is quiet, below UI clicks, typing and caption pops. Typing sounds play only while text is visibly appearing.

- Ship the captioned original and a Nader-narrated cut by default. A brief may request a different cut for that video only. Nader is the only narrator: voice ID `T8iHhGIWPm2GVYpQD1Am`, output name `nader`. Never generate other narrators, including on redos whose old briefs/templates name another voice. Leave unrelated legacy voice files/README rows already on main untouched unless asked.
- With `ELEVEN_LABS_API_KEY` securely available, use the normal current one-take path from `tutorials/`:
  ```sh
  python3 _kit/tools/vo.py <folder> T8iHhGIWPm2GVYpQD1Am
  VOICE=T8iHhGIWPm2GVYpQD1Am VO_NAME=nader SEG=1500 JPEG_QUALITY=85 bash _kit/tools/build.sh <folder>
  ```
  It sends the whole ordered script in one request with `text` and `model_id`, omitting `seed` and `voice_settings` so the voice's saved/default behavior applies. It cuts locally, keeps lead-in to avoid clipping first consonants, verifies the transcript/boundaries, and writes per-line WAVs plus `vo/<voice-id>/lines.json`. Do not substitute a seeded legacy recipe, hard-code stability/similarity/style/speed, pass `next_text`, or return to per-sentence requests.
- Current caching is whole-take, not per-line: unchanged text with a complete matching manifest/WAV set is reused; any script change regenerates the full take. For an explicitly requested fresh take of identical text, preserve approved files outside the production folder and remove the old `lines.json` cache before rerunning; there is no force flag in current `vo.py`. Retries generate another complete take, not only failed lines.
- Rerecord the entire script and re-split it when wording, punctuation or tone needs fixing, or when asked to redo the script. Selective retakes are allowed only when specifically requested/approved; keep the same voice/default request and verify the seam. Inspect the request and shared `take` value before claiming single-take provenance.

### Writing and listening

- Open with what the feature does and why it matters, not "This is Devin X". Explain the demo objective before its prompt and cover key autonomous behavior from the docs, not only the user-triggered path visible in the footage.
- Write logically distinct complete sentences. Never split a sentence across beats, end on a lead-in, or cram separate thoughts into run-on comma/colon lists. Prefer fewer, fuller sentences across related actions without forcing every thought into one long sentence. Keep plain wording and natural cadence; avoid awkward repeated words and tutorial-specific stock phrases.
- Listen end to end for clipped consonants, dull closing lines, rushing, unnatural comma pauses and rising/unfinished endings. Transcript checks do not judge tone. Rephrase and rerecord when a pause problem affects tone instead of mechanically trimming silence. Preserve deliberate natural sentence pauses, not an identical imposed gap after every line.
- Display menu paths with arrows in `vo`/captions (e.g. "Settings → Playbooks"); use `voSay` only when spoken pronunciation/punctuation needs to differ. Keep its sentence structure compatible with displayed `vo`, regenerate the take and subtitle chunks, and check timing/word coverage. Say "Devin" except when clicking the "Devin Local" label; display "SWE-2" while `voSay` says "swee two".
- Keep names, digits and file paths pronounceable. The transcript check compares against displayed `vo` with existing aliases, not just `voSay`; prefer natural wording it can verify. `voOutro` has no separate `voSay` field, so avoid words needing a pronunciation override there.
- The Nader voice reads the heteronym "live" as "liv". Respelling it as "lyve" in `voSay` gave mixed results, so reword instead ("public URL", "the page running on Modal"). Say "xAI" as "ex A I".

### Layout, timing and coverage

- With voice enabled, ordinary `cap` captions are replaced by word-timed subtitles and music ducks under the voice. Caption auto-placement does not position voice subtitles. Use per-beat `subPos` (`'side'`, `'left'`, `'right'`, `'top'`, `'bottom'`) or a safe spec default: beside controls in clear empty space for setup/menu/terminal/dialog scenes; a safe bottom band for sessions only if it avoids the composer, controls, search/helper text and described content. Inspect both cuts at every cue and crossfade.
- Put `vo` on the beat where the line starts and `voOutro` on the spec for the outro. Use `voSync` (seconds into the current line), `waitVo` and `voDelay` to keep actions aligned with speech. Match diagram/list/recap/stat/attribution reveals to when narration names each item, not a fixed stagger racing ahead. Refit after every regeneration.
- Run `VOICE=T8iHhGIWPm2GVYpQD1Am node _kit/tools/render.mjs <folder> --count` as a duration/late-cue check. It is not a complete silence or missing-line check. Audit actual `window.film.cues().vo` / generated `build/cues.json` against `vo/<voice-id>/lines.json`, listen to the final mix, and measure rendered word gaps (STT if needed; music can defeat `silencedetect`). Ordinary narration gaps should be about 1.5 s or less, with narration waiting on visuals around 1 s or less. Preserve purposeful natural pauses; explicitly justify any longer deliberate pause or real-call exception. Check every line, including the last line to the outro.
- **Current implementation caveat:** `vo.py` emits `takeAt`, not the `at`/`end` fields used by the engine's `voNatural` branch. Do not assume the rendered timeline preserves original take pause lengths automatically. Verify actual cues and tune cut-specific `hold`, `voGap`/`voSentGap`, `tailHold` and `outroVoDelay` as needed. `outroVoDelay` is the UI-end-to-outro-voice delay; earlier holds and tail timing also contribute.
- Apply narration-only hold/timing overrides in `spec.js` so an approved captioned cut stays unchanged when only narrated pacing changes. Current `vo.py` parses a strict JSON object after `window.SPEC =`, not arbitrary executable JS. If runtime layout branches on the voice query, preserve a strict-JSON narration input and use the chosen folder's existing generation/build workflow rather than copying runtime-only JS into the TTS input.
- After moving/skipping beats, confirm every intended line (including intro/outro) has a cue, correct WAV and manifest key. Rename/remap consistently and regenerate subtitle chunks when necessary; `--count` alone does not prove coverage. Moving a line earlier without trimming the following narrated hold can simply relocate silence.
- For the opening, STT may hear the chime as "[on-hold music]"; inspect the first spoken word time and waveform instead. Real live voice-call content is a separately scoped timing exception, not permission for long silent editorial waits.

### Files and delivery

- Style overrides from a per-video brief (e.g. "dark mode") use the kit's opt-in switches, such as `dark: true` in `spec.js` (`SPEC.dark`; scenes get `o.DARK`/`o.INK`/`o.BG`). Do not fork `_kit/src/engine.js` per video. If a batch needs a new kit option, the coordinator lands one shared kit PR before fanning out.
- Voice builds write `<folder>-nader.mp4` without overwriting the captioned original/poster. Keep narrated README entries in the root "Narrated tutorials" section. Use separate focused PRs when adding narration to an existing captioned delivery; never base a follow-up on an already merged tutorial branch—use current main.
- Current `vo.py` removes its temporary `_take.wav` at completion. Never commit that file, `_full-take.wav` or any full-script scratch audio. When ElevenLabs throttles parallel work, coordinate/retry the whole-take path rather than reverting to per-line synthesis.
- Older loose-JS specs need a strict-JSON narration spec before using `vo.py`. Keep runtime-only layout code separate from that input; do not invent unsupported command flags.
- If specifically requested, make a separate clean/music-only cut with `noCaps: true` and no voice input, using a temporary spec without changing the production original. Dropping `cap` only from overrides is insufficient because beats also carry captions. Verify remaining scene text/captions.
- Attach the narrated preview and full Markdown voice script in chat. Do not unnecessarily rebuild an approved captioned cut for narration-only revisions.

## Feature-specific capture recipes

The following sections preserve useful observations from earlier takes. Reverify current docs, UI labels, permissions, timings and folder availability; they are not universal guarantees.

## Native apps (Devin CLI, Devin Desktop)
- Record the real installed app, never a mock. CLI: run `devin` in tmux and render the pane through `_kit/capture/term/termrec.mjs` (xterm.js, JetBrains Mono at 21 px, 3× scale), which keeps terminal text crisp and readable at the whole-screen framing. Resize the tmux window to the xterm grid before starting so lines don't wrap. Desktop: attach to the Electron app over CDP (`--remote-debugging-port=9335`) with `_kit/capture/desktop.mjs`, set the viewport to 1280×720 at 3× so the UI renders large and sharp, and bring the app to the front first (`open /Applications/Devin.app`), since background windows stall screenshots.
- Use a clean demo repo (e.g. Orbit) and a small, visible UI feature. In Desktop, finish by showing it working in Desktop's own localhost preview pane, and caption that it is the app running on localhost. In the CLI, skip the browser demo: end the local part on the edits being on disk and move on to the CLI's own features.
